DNS and Nginx "fill gaps"

Just like Rocky and Adrienne, Nginx and DNS "fill gaps," each having distinct responsibilities for getting a request from a user's browser to your application.

Separation of Concerns
Domain → IP IP → Your Application
DNS Nginx
DNS: Domains to IPs
I'm not going to delve too deeply into this, since it is covered in any introductory networking resource in far more detail than I really care to go into, but the key point that was driven home to me by looking at the issues with going from my domain to my application's home page was that DNS, given a domain, will give you an IP. This is obviously very powerful, but that is (essentially) all that you are looking for when you create your various DNS records: create the ability to route traffic from your domain to your server/load balancer/ingress.
Nginx: IP to Your Application (via Reverse Proxy)

Once the request arrived at my IP address, I started to appreciate how Nginx's ability to perform as a Reverse Proxy allowed it to route requests once they had arrived at the instance

TLDR Nginx's Reverse Proxy capability allowed me to ensure that when my brother-in-law typed https://www.missour.ai he was sucessfully redirected to the port and route where my application was hosted without having to enter the port and route each time into the browser's URL bar.

Conceptual Overview

Before I write out the Nginx configuration that I used to accomplish this task, I am going to describe (to the best of my understanding) what is happening when a user types in https://www.missour.ai to establish a conceptual understanding of what missing pieces Nginx provides

  1. Browser sends an HTTP/HTTPS request to the DNS server
  2. Request gets an IP address from the DNS server
  3. Request gets to the IP address
  4. Your application is being hosted on a specific port (usually 8000 in Django) and route (indicated in urls.py in Django) on that server
At that point, you can see where the problem lies: between steps three and four. Without the user explicitly entering the port and route information into the browser, the request doesn't have the information required to "find its way" to your application. This is where Nginx as a Reverse Proxy comes in: it provides the request with those "directions."

Walking through the Code

With this framing in mind, let's begin to go through the most relevant portions of the default.conf for this topic that is hosted in my application's GitHub. 

    
server {
listen 80;
...
}

server {
listen 443 ssl;
...
}
    • Tells Nginx which ports to listen on for incoming traffic
    • Ensure that Nginx can receive the HTTP and HTTPS traffic that the browser is sending
    • If Nginx never receives the request, it can't provide the request with the "directions" to the application
    
server {
...
server_name missour.ai www.missour.ai;
...
}
    • This block, in something of a juxtaposition to the previous block, is intended to ensure that only the correct traffic gets handled by your application
    • Go to a website, open the DevTools Network Tab, hit the record button, reload a page, stop recording, and then click on one of the files being loaded
    • Click on the "Headers" tab and find the "Host" entry.
    • This section of the default.conf ensures that there is a "handshake" between what is in the "Hosts" portion of the HTTP/HTTPS header and your server block, which in turn avoids accidentally serving your application
    • There are also certificate issues this helps address, but I will cover that in the next section.
    
server {
listen 443 ssl;
...

location = / {
return 302 /transcription/;
}

location / {
proxy_pass http://web:8000;
...
}
}
    • The first concept to understand here is the difference between exact and prefix matches
      • Exact Match: Matches the **exact** URI. This is the type of match given in the location = / code block.
      • Prefix Match: Matches **anything** that starts with the prefix (i.e. "/")
    • Nginx chooses the most specific paths first when making routing decisions, so it will use the information provided in the exact match first and redirect the user to /transcription/.
    • From there, Nginx falls back onto the prefix match (i.e. location /)
    • Within that location block, you can see that there are three components: http://, web, :8000
      • http:// and :8000: These two relate to the protcol and port that the asgi/wsgi server is listening on. Since I am using Uvicorn, I fell in on these values and this is likely to be boilerplate across various Nginx default.conf files.
      • web: This matches the name of the service that I gave my Django application in my docker-compose.yml. I am sure that this "synching" is something I will have to dig into at some point, but at this point I've gotten pretty comfortable with deploying applications on my own with Docker Compose and am content for now with this being a piece of trivia that is something of a black box.
    • You will notice that the URI redirected to during the exact match (i.e. /transcription/) is noticably absent from the proxy_pass
    • The reason for this is because if you don't include a URI within the proxy_pass, the original URI that was passed is preservered. In this case, you get /transcription/ in and /transcription/ out. This functionality is covered, somewhat confusingly in my opinion, in the portion of the Nginx documentation on proxy_pass
    
server {
listen 80;
...

location / {
return 301 https://$host$request_uri;
}
}
    • You may notice that in the last code block, we were listening on port 443 for HTTPS traffic, but in this code block we are listening on port 80.
    • The reason for this is because we want to ensure that users are able to reach the application via either an HTTP or HTTPS connection, but we want them to be redirected to HTTPS for security reasons.
    • We accomplish this goal with the location / { return 301 ... } block which ensure that users, when they go to "http://missour.ai" automatically get redirected to the same location via HTTPS (as indicated by the 301 HTTP status code).
    • In order to redirect to the same location, you use two variables ($host and $request_uri) that Nginx "automagically" creates based on an incoming request.

Putting it all Together

Having gone into that detail, I want to resurface the initial problem that I faced that led me to Nginx in the first place: How can I make sure that my brother in law doesn't have to enter https://missour.ai:${port}/${route} and can instead cleanly go to https://missour.ai? Nginx, as ChatGPT told me, allows that to happen, but now I feel more comfortable in explaining the how. For me, the most useful way to illustrate that is through revisiting the conceptual analysis of the request that I presented earlier.

  1. Browser sends an HTTP/HTTPS request to the DNS server (No change)
  2. Request gets an IP address from the DNS server (No change)
  3. Request gets to the IP address on port 80 or 443
  4. Nginx
    • Listening on Port 80/443
    • Validates the Host header
    • Redirects to Port 8000
      • HTTPS: https://missour.ai -> https://missour.ai/transcription -> https://missour.ai:8000/transcription (This is where your application is being served)
      • HTTP: http://missour.ai -> https://missour.ai -> HTTPS path
  5. Request arrives at your application

This, however, left be curious, as to why this was best practice.

Don't I already have a web server?

The first thing that was confusing to me was that Nginx was not mentioned in the main How to deploy section of the Django docs. It was featured in the discussion on static files for reasons related to speed, but I was getting the feeling that Nginx wasn't STRICTLY required to sit in front of Uvicorn. The Deployment section of the Uvicorn documentation that speaks to "Running behind Nginx" expresses exactly that sentiment

Using Nginx as a proxy in front of your Uvicorn processes may not be necessary, but is recommended for additional resilience. Nginx can deal with serving your static media and buffering slow requests, leaving your application servers free from load as much as possible.

At this point, I felt like understanding the exact why behind "stacking" Nginx and Uvicorn was performance related, which was not really going to gain me very much at the moment given that my project has an audience of one who is willing to tolerate a lack of "snappiness." That being said, I did feel like understanding the how, at least from the vantage point of my Python code, Uvicorn was working. As I looked into this I came to realize that ...

asgi.py and wsgi.py are basically fancy main.py files

When I write Python programs, I generally try to write various different modules that I tie together in a single main.py file, and I think that most people do this as well. As I started to put together my asgi.py file and its relationship to the command that ChatGPT told me to put into my Dockerfile to run to get my application running, informed by some ModuleImportError issues relating to file paths and the Django ASGI documentation, I noticed that I was being walked into a similar pattern with Django to the one that I normally use with a main.py. I had a "core" file, in this case asgi.py, that I imported various packages into, in this case my Django application. If you look at the Uvicorn Documentation's Running programmatically section, you'll even see that it covers running Uvicorn from a main.py! That being said, I knew that there was SLIGHTLY more to what was going on here than my useful but incomplete "main.py by another name", since not any old main.py can serve web requests.

TLDR: Uvicorn, and other ASGI servers mentioned in the Django documentation like Daphne and Hypercorn, provide a wrapper that allows a Python application to meet the requirements for serving web traffic asynchronously, requirements that are laid out within the ASGI Specification

Conceptual Overview

Similar to above, I want to walk through what is happening conceptually before diving into the details.

  1. People define what an ASGI web server in Python needs to be able to do
  2. People write ASGI web servers that do the things laid out above
  3. Django asgi.py creates a situation where uvicorn asgi.py ~ python main.py
  4. Invoke your web server and point it at the asgi.py

Walking Through the Code (and Docs)

ASGI (Asynchronous Server Gateway Interface) is a spiritual successor to WSGI, intended to provide a standard interface between async-capable Python web servers, frameworks, and applications. - ASGI Documentation

To me, standard interface the key portion in this to understand what ASGI is. An interface's dictionary definition is "a point where two systems, subjects, organizations, etc. meet and interact," and ASGI describes the details of what to expect at that interaction point. I think that looking at the Events section of the ASGI documentation provides some good color on how those details are laid out: "Each event is a dict with a top-level type key that contains a Unicode string of the message type... Because these messages could be sent over a network, they need to be serializable, and so they are only allowed to contain the following types: Byte strings, Unicode strings, Integers (within the signed 64-bit range), Floating point numbers (within the IEEE 754 double precision range; no Nan or infinities), Lists (tuples should be encoded as lists), Dicts (keys must be Unicode strings), Booleans, None." This is a fairly detailed description of what to expect in an event, and people sending and receiving events to know what to expect (very useful to Django developers working to make the framework ASGI friendly!).

Uvicorn is an ASGI web server implementation for Python. - Uvicorn Docs

Once again, I highlighted what I think is the key term: implementation. ASGI tells people what to build, then people need to build it! Uvicorn, and other pieces of software, are projects that bring ASGI to life. These ASGI implementations consist of two components: a protocol server and an application where the application lives within the protocol server. You can see this application within my application's asgi.py file: 


"""
ASGI config for missourai_web_app project.

It exposes the ASGI callable as a module-level variable named ``application``.

For more information on this file, see
https://docs.djangoproject.com/en/5.1/howto/deployment/asgi/
"""

import os

from django.core.asgi import get_asgi_application

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'missourai_web_app.settings')

application = get_asgi_application()

The auto-generated comment at the start of the file directs you to the documentation, but you can pretty simply piece together what is happening here

  1. Import the get_asgi_application function: from django.core.asgi import get_asgi_application
  2. Point get_asgi_application function to your Django application's settings file: os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'missourai_web_app.settings')
  3. Create the application callable: application = get_asgi_application()


CMD ["/app/.venv/bin/uvicorn", "missourai_web_app.asgi:application", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]

Since the code in the asgi.py made the application "callable," you can now use an "ASGI Implementation" like Uvicorn to allow your application to receive HTTP/HTTPS/Web Socket traffic, as shown above from my Dockerfile.

Putting it all Together

I think that the simplest way to understand my original question of how Uvicorn is working is to map Django code to the "ASGI Components" laid out in the ASGI Documentation: the Application and the Protocol Server.

Reference Chain
File Relevant Code Application Reference ASGI Component
asgi.py os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'missourai_web_app.settings') missourai_web_app.settings (defined within settings.py) Application
Dockerfile CMD ["/app/.venv/bin/uvicorn", "missourai_web_app.asgi:application", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"] missourai_web_app.asgi:application (defined within asgi.py) Application Server

As you can see in the table above settings.py → missourai_web_app.settings in asgi.py → missourai_web_app.asgi:application in the Uvicorn invocation, and how these map cleanly onto some of the abstract concepts discussed in the ASGI Documentation
